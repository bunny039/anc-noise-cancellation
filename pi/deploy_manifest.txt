================================================================
CLEARCOM DEPLOYMENT GUIDE -- COMPLETE FILE-BY-FILE WALKTHROUGH
================================================================

This guide tells you EXACTLY which files go on the Pi, what each
file does, how to set up, and how to run.


================================================================
SECTION 1: WHAT CHANGED (OLD vs NEW)
================================================================

OLD SYSTEM (30-second delay):
  - Audio captured -> accumulated into LARGE buffer -> processed
    as one big ONNX chunk -> THEN sent over UDP
  - Single-threaded: capture WAITS for enhance to finish, enhance
    WAITS for send to finish -> everything is SERIAL
  - Result: audio piles up in buffers, each chunk waits for the
    previous one to finish, creating a 30-second backlog

NEW SYSTEM (under 1 second):
  - 5 THREADS run AT THE SAME TIME (simultaneously):
    Thread 1: Captures mic audio continuously
    Thread 2: Enhances chunks as soon as they arrive
    Thread 3: Sends enhanced audio as 20ms UDP packets
    Thread 4: Receives UDP packets from peer
    Thread 5: Plays received audio through speaker

  - BOUNDED QUEUES (max 3 items): if Thread 2 (enhance) is too
    slow and Thread 1 (capture) has filled the queue, the OLDEST
    unprocessed chunk is DROPPED. This means:
    * You might lose 0.25s of audio occasionally
    * BUT you are NEVER more than ~0.5s behind real-time
    * No more 30-second buildup

  - SMALLER CHUNKS: 0.25 seconds instead of 1-2 seconds
    * Less audio to process per ONNX call
    * Less time waiting for a chunk to fill up
    * Less latency

  - ECHO GATING: when the peer's voice is playing through your
    speaker, your mic is soft-muted (gain=0.05) so the speaker
    output does not feed back into the mic and cause interference

SECTION 2: FILES TO COPY TO EACH PI
================================================================

Copy the entire pi/ folder. The structure on the Pi:

  ~/clearcom/
  |
  |-- udp_stream.py           <-- MAIN SCRIPT (you run this)
  |-- df_onnx_dsp.py          <-- ONNX DSP engine (don't touch)
  |-- config_pi.yaml          <-- settings (edit Bluetooth devices)
  |-- requirements-pi.txt     <-- pip dependencies
  |-- test_local.py           <-- optional self-test
  |
  |-- models/
  |   |-- enc.onnx            <-- ONNX encoder (1.9 MB)
  |   |-- erb_dec.onnx        <-- ONNX ERB decoder (3.3 MB)
  |   |-- df_dec.onnx         <-- ONNX DF decoder (3.3 MB)


================================================================
SECTION 3: FILE-BY-FILE EXPLANATION
================================================================

--- udp_stream.py ---

  WHAT: The main entry point. Starts 5 threads for full-duplex
        streaming with ONNX noise cancellation.

  PIPELINE IT RUNS:
    Bluetooth mic (16kHz s16le)
      -> accumulate 0.25s of audio (4000 samples)
      -> resample 16kHz to 48kHz (12000 samples)
      -> run DeepFilterNet3 ONNX model (48kHz)
      -> resample 48kHz back to 16kHz (4000 samples)
      -> split into 20ms packets (640 bytes each, s16le)
      -> send via UDP to peer Pi

    AND SIMULTANEOUSLY:
    receive UDP packets from peer (640 bytes, 20ms, s16le)
      -> play through Bluetooth speaker via PulseAudio

  HOW TO RUN:
    Manager Pi:  python3 udp_stream.py --role manager
    CEO Pi:      python3 udp_stream.py --role ceo

  HARDCODED IPs AND PORTS:
    Manager (10.29.30.109) sends to CEO port 5000
    CEO (10.29.30.163) sends to Manager port 5001
    These are in the ROLES dict at the bottom of the file.
    Change them if your Pi IPs change.


--- df_onnx_dsp.py ---

  WHAT: The ONNX inference + DSP engine. Does the actual noise
        cancellation math: STFT, ERB filterbank, feature
        normalization, run 3 ONNX models (encoder, ERB decoder,
        DF decoder), apply mask + deep-filter coefficients, iSTFT.

  DO NOT EDIT THIS FILE unless the ONNX model itself changes.

  KEY FUNCTION: enhance_chunk(audio_48k, enc, erb_dec, df_dec, erb_inv_fb)
    - Input:  float32 numpy array at 48 kHz
    - Output: enhanced float32 numpy array at 48 kHz


--- config_pi.yaml ---

  WHAT: Configuration file. Controls:
    - chunk_seconds: how much audio to buffer before processing
      (0.25 = 250ms, the sweet spot for latency vs quality)
    - queue_maxsize: how many chunks can queue up (3 = ~0.75s max)
    - echo_gate: whether to mute mic during speaker playback
    - pulseaudio source/sink: your Bluetooth device names

  EDIT THIS FILE to set your Bluetooth device names:
    1. Run: pactl list short sources
       Find your Bluetooth mic, e.g. "bluez_source.24_01_08_16_00_B0"
    2. Run: pactl list short sinks
       Find your Bluetooth speaker, e.g. "bluez_output.24_01_08_16_00_B0.1"
    3. Put them in config_pi.yaml under pulseaudio: source: and sink:

  OR pass them as command-line arguments:
    python3 udp_stream.py --role manager \
      --pulse-source bluez_source.24_01_08_16_00_B0 \
      --pulse-sink bluez_output.24_01_08_16_00_B0.1


--- models/enc.onnx, erb_dec.onnx, df_dec.onnx ---

  WHAT: The three ONNX model files that make up DeepFilterNet3.
        Already trained on military/defence noise data.
        DO NOT retrain or modify -- just copy them to the Pi.

  enc.onnx     = encoder network (extracts features)
  erb_dec.onnx = ERB decoder (produces spectral mask)
  df_dec.onnx  = DF decoder (produces deep-filter coefficients)

  These expect:
    feat_erb -> erb_m (spectral mask)
    feat_spec -> df_coefs (deep-filter coefficients)
  with config: sr=48000, fft=960, hop=480, 32 ERB, 96 DF, order 5


--- requirements-pi.txt ---

  WHAT: Python package dependencies to install on the Pi.
  KEY PACKAGES:
    numpy         - array math
    onnxruntime   - runs the ONNX models (prebuilt aarch64 wheel)
    scipy         - resampling 16kHz <-> 48kHz
    soundfile     - (kept for compatibility)
    pyyaml        - reads config_pi.yaml
    sounddevice   - (kept for compatibility, not used by main script)


================================================================
SECTION 4: SETUP ON EACH PI (one-time)
================================================================

STEP 1: Copy files to the Pi
  From your Windows machine:
    scp -r pi/ pi@10.29.30.109:~/clearcom/     (Manager Pi)
    scp -r pi/ pi@10.29.30.163:~/clearcom/     (CEO Pi)

STEP 2: SSH into the Pi
    ssh pi@10.29.30.109     (Manager)
    ssh pi@10.29.30.163     (CEO)

STEP 3: Install Python dependencies
    cd ~/clearcom
    pip3 install -r requirements-pi.txt

STEP 4: Verify PulseAudio and Bluetooth
    # Check PulseAudio is running
    pulseaudio --check && echo "PulseAudio OK" || echo "NOT RUNNING"

    # List Bluetooth sources (mic)
    pactl list short sources | grep bluez

    # List Bluetooth sinks (speaker)
    pactl list short sinks | grep bluez

    # Note down the source and sink names for your headset

STEP 5: Edit config (if not using CLI args)
    nano config_pi.yaml
    # Set pulseaudio: source: and sink: to your Bluetooth device names

STEP 6: Test that ONNX models load
    python3 -c "from df_onnx_dsp import load_sessions; load_sessions('models'); print('OK')"

STEP 7: Test mic capture works
    parec --rate=16000 --channels=1 --format=s16le --raw | head -c 32000 > test_mic.raw
    # This should record 1 second (32000 bytes) from your mic
    # If it hangs or errors, your PulseAudio/Bluetooth source is wrong

STEP 8: Test speaker playback works
    # Generate a test tone and play it
    python3 -c "
    import numpy as np
    t = np.arange(16000) / 16000.0
    tone = (0.3 * np.sin(2 * 3.14159 * 440 * t) * 32767).astype('<i2')
    tone.tofile('test_tone.raw')
    "
    pacat --rate=16000 --channels=1 --format=s16le --raw --playback < test_tone.raw
    # You should hear a 1-second 440 Hz beep


================================================================
SECTION 5: RUNNING THE SYSTEM
================================================================

On Manager Pi (10.29.30.109):
    cd ~/clearcom
    python3 udp_stream.py --role manager

On CEO Pi (10.29.30.163):
    cd ~/clearcom
    python3 udp_stream.py --role ceo

BOTH commands must be running at the same time.

OPTIONAL: specify Bluetooth devices explicitly:
    python3 udp_stream.py --role manager \
      --pulse-source bluez_source.24_01_08_16_00_B0 \
      --pulse-sink bluez_output.24_01_08_16_00_B0.1

WHAT YOU SHOULD SEE:
    ======================================================================
    CLEARCOM UDP STREAMING -- MANAGER PI
    ======================================================================
      Role:           manager
      Pipeline SR:    16000 Hz (UDP)
      ONNX SR:        48000 Hz (model)
      Chunk:          0.25s (4000 samples @ 16kHz)
      Packet:         20ms (640 bytes s16le)
      Peer IP:        10.29.30.163
      Send port:      5000
      Recv port:      5001
      ...

    Then every 3 seconds:
    [status] enhanced=12 | sent=12 | recv_pkts=156 | enhance_ms=180

    "enhanced" should keep growing -- this means chunks are being processed
    "sent" should match enhanced -- chunks are being sent to peer
    "recv_pkts" should keep growing -- you are receiving from peer
    "enhance_ms" is the time per chunk -- should be < 250ms on Pi 4


================================================================
SECTION 6: TROUBLESHOOTING
================================================================

PROBLEM: "parec not found"
  FIX: sudo apt install pulseaudio pulseaudio-module-bluetooth

PROBLEM: No Bluetooth device in pactl list
  FIX: Pair and connect the Bluetooth headset first:
    bluetoothctl
    > scan on
    > pair XX:XX:XX:XX:XX:XX
    > connect XX:XX:XX:XX:XX:XX
    > trust XX:XX:XX:XX:XX:XX
    > quit

PROBLEM: enhance_ms > 250 (slower than chunk duration)
  FIX: Increase chunk_seconds in config_pi.yaml to 0.5
       This gives more processing time but adds ~250ms latency

PROBLEM: capture_drops > 0
  MEANING: Enhancement is too slow, chunks are being dropped
  FIX: Normal if occasional. If constant, increase chunk_seconds

PROBLEM: No audio from peer
  CHECK: Can the Pis ping each other?
    ping 10.29.30.163  (from Manager)
    ping 10.29.30.109  (from CEO)
  CHECK: Is the firewall blocking UDP?
    sudo ufw allow 5000/udp
    sudo ufw allow 5001/udp

PROBLEM: Echo / feedback
  FIX: Echo gate should handle this. If not, try:
    - Use headphones instead of speaker
    - Increase mute_gain from 0.05 to 0.0 (full mute) in config
    - Increase holdoff_packets from 10 to 20

================================================================
SECTION 8: LATENCY BREAKDOWN
================================================================

WHERE THE TIME GOES (estimated for Pi 4):

  Mic capture buffer:    250 ms  (0.25s chunk accumulation)
  Resample 16k->48k:     ~5 ms
  ONNX enhancement:   ~180 ms  (the big one -- model inference)
  Resample 48k->16k:     ~5 ms
  UDP send/receive:      ~5 ms  (Wi-Fi LAN)
  PulseAudio playback:  ~20 ms  (one packet buffer)
  -----------------------------------------
  TOTAL:               ~465 ms  (under 0.5 seconds)

  vs OLD SYSTEM:       ~30000 ms  (30 seconds)

  WHY 60x FASTER:
  1. Chunks are 0.25s not 2.0s          (8x less buffering)
  2. 5 threads run AT THE SAME TIME     (no serial waiting)
  3. Bounded queues DROP old chunks     (never accumulate backlog)
